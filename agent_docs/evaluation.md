# Evaluation

## Metrics (computed from parquet traces, per `architecture.md`'s trace schema — never from live state)

- **Tracking RMSE**: RMSE of `(pitch - target_pitch, roll - target_roll)` over a window. Reported per-scenario overall, and separately pre-fault vs. post-fault for the fault/combined scenarios.
- **Settling time**: steps until tracking error first enters and stays within a tolerance band (define the band in `configs/experiment/*.yaml`, keep it consistent across controllers for a given scenario).
- **Control smoothness (jerk)**: mean absolute second derivative of each action channel over time. High jerk under a learned online update can indicate an unstable or oscillating adaptation — worth plotting alongside recovery, not just reporting as a scalar.
- **Time-to-recover (fault/combined scenarios only)**: steps from fault onset until tracking RMSE (computed over a trailing window) returns to within a factor of its pre-fault value (e.g. 1.2×) and stays there for the rest of the episode. A controller that never returns is recorded as "did not recover" (infinite / censored), not silently dropped from the average — censored runs must be reported as a rate ("recovered in 8/10 seeds"), not averaged in as if they were large finite numbers.

## Statistical protocol

- N=10 seeds per (controller, scenario, severity) cell by default (see `experiments.md`).
- Report median and IQR (not mean ± std) for RMSE/settling-time/jerk — flight-dynamics metrics are heavy-tailed (occasional large excursions), median is more honest here.
- For the headline RTRL-vs-frozen-BPTT-LSTM comparison in the fault scenario: paired comparison (same seeds, same fault draw) where possible, Wilcoxon signed-rank over per-seed time-to-recover / post-fault RMSE, not just an eyeballed plot.
- For the ablation (online-on vs. online-off): same paired approach, same seeds and fault draws between the two runs — this is the whole point of holding everything else fixed in `experiments.md` scenario 5.

## What "RTRL recovers, frozen BPTT-LSTM does not" means numerically

Not just "RTRL's post-fault RMSE is lower." Report both:
1. RTRL's post-fault RMSE returns to within the settling-time recovery band (defined above) within the episode.
2. Frozen BPTT-LSTM's post-fault RMSE does not enter that band for the remainder of the episode (or takes materially longer — report the actual numbers, don't just threshold to a binary).

If both recover but RTRL is merely faster, that's a real but weaker result than the framing in `project_overview.md` implies — report it accurately rather than reframing the success criterion after the fact.

## Plots (generated by `src/rtrl_flight/analysis/`, from parquet)

- Time series of tracking error and commanded action around fault onset, one panel per controller, overlaid across seeds (median + IQR band).
- Time-to-recover distribution (box or strip plot) per controller, per fault severity.
- Ablation comparison: online-on vs. online-off, same layout as the fault-scenario recovery plot, side by side.
- Nominal-scenario sanity check: RMSE distribution per controller, confirming the ~15% bar from `experiments.md`.

## Reproducibility check before trusting any of the above

Confirm the run's Hydra output dir has config + seed + git SHA + W&B run ID (per CLAUDE.md). If a result can't be traced back to a specific config and commit, don't include it in analysis, regenerate it first.
